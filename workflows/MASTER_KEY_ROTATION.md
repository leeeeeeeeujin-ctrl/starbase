# Master Key Rotation & Runbook

목표: `MASTER_KEY_HEX` (마스터 키) 교체 시 안전한 절차와 롤백 계획을 문서화합니다. 이 문서는 디바이스 비밀, 암호화된 시크릿, 그리고 마이그레이션 시 영향을 받는 구성요소를 고려합니다.

전제
- 현재 시스템은 `MASTER_KEY_HEX`를 사용해 디바이스 비밀 등 민감값을 암호화합니다.
- 키 교체는 운영상 민감한 작업이므로 사전 테스트와 단계적 롤아웃이 필요합니다.

절차 (요약)
1. 준비(로컬/스테이징)
   - 새 마스터 키 생성: 안전한 랜덤(예: `openssl rand -hex 32`)으로 새 키를 생성합니다.
   - 스테이징 환경에 새 키를 배포하고, 암호화/복호화 루틴이 정상 동작하는지 확인합니다.
2. 데이터 이동(재암호화)
   - 기존 저장소(예: devices table 또는 파일 백엔드)의 각 암호화된 값에 대해: 복호화(구키) → 암호화(신키) → 저장.
   - 이 작업은 배치로 실행하고, 배치가 실패하면 롤백(원키로 유지) 상태를 보장.
3. 점진적 교체
   - 앱 인스턴스와 CI에 새 키를 환경 변수로 추가하되, 기존 키(구키)도 읽기용으로 유지합니다. 운영 코드는 먼저 '구키, 신키 순으로 복호화 시도'하도록 지원해야 합니다.
   - 모든 새 쓰기 작업은 신키로 암호화합니다.
4. 검증
   - 테스트 디바이스 등록/검증 플로우를 실행해 복호화가 정상인지 확인.
   - 자동화된 무결성 검사(랜덤 샘플 복호화 후 원본과 비교) 실행.
5. 구키 제거
   - 신키만으로 모든 항목이 성공적으로 암호화된 것이 확인되면, 일정 기간(예: 7일)의 보류 기간을 거친 후 구키를 제거합니다.

롤백 계획
- 재암호화 도중 문제가 발견되면 즉시 작업을 중단하고, 서비스는 구키를 기준으로 계속 동작한다는 것을 보장해야 합니다.
- 구키 제거 전까지는 언제든 구키로 복구 가능해야 합니다.

운영 체크리스트
- 새 키 생성(보안 검토)
- 스테이징에서 암복호화 검증
- 배치 재암호화 스크립트(샘플 포함) 준비
- 모니터링/로그(성공/실패 카운트)
- 구키 보관소(오프라인 또는 HSM 권장)

간단한 재암호화 스크립트(예제, pseudo)
```bash
# PSEUDO: iterate over devices, decrypt with OLD_KEY, encrypt with NEW_KEY
node scripts/reencrypt_devices.js --old $OLD_KEY --new $NEW_KEY
```

권한/보안 권고
- 마스터 키는 가능한 경우 HSM 또는 cloud KMS(예: AWS KMS)로 관리하세요.
- 마스터 키가 노출되면 즉시 회전하고, 관련 비밀(예: device secrets)을 재발급해야 합니다.
